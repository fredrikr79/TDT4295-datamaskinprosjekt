# MCU <-> FPGA SPI protocol description.

For HEX's MCU <-> FPGA communication channel, we're utilizing a custom OCTO-SPI driver paired with dedicated hardware on the STM32. Since the dedicated hardware places fixed limitations on the timings and sequences of transmissions, the driver contains a few important implementation details and protocol constraints.

## Interface
The FPGA exposes the following signals to the MCU for the OCTO-SPI protocol:

- `ck_sck` : The MCU generated SPI clock signal. It is used to time RX sampling TX events.
- `ck_ss` : Active-low MCU driven chip select signal used by the MCU to indicate an active transaction.
- `Ready` : Active-high FGPA generated signal telling the MCU that the FPGA is waiting for the MCU to initiate the next step of the protocol. 
- `ACK` : Currently unused. Intended to acknowledge an understood command post RX.
- `octo_spi [7:0]` : 8 bit bidirectional data bus used for transferring command and response data between the MCU and FPGA  

### Hidden components:


- `in_fifo` : A `1024` byte FWFT FIFO buffer used to store all data associated with the current command.
- `out_fifo` : A `1024` byte Standard FIFO buffer used to store the response data generated by the current command.

NB! Both buffers will be cleared before a new instruction can be issued. Therefore you cannot pre-buffer instructions. This is a decision made to ensure that an invalid state of the in-buffer is automatically recoverable from the FPGA's standpoint.

## The basic protocol

To illustrate the basic protocol, we will trace a simple echo command in its full round-trip from boot time til finish.

The general protocol is: `BOOT -> READY -> RX -> DECODE -> BUSY -> TX_IDLE -> TX_SEND -> READY`

The different steps are described in more detail below.

### Boot state
During boot, the FPGA will await the initialization of the `in_fifo` and `out_fifo`. Once the ports are establised it drives the `Ready` signal to `HIGH`, signaling the MCU that it is ready for a command to be issued.

### Ready state
The state used by the FPGA to signal that no command is currently in the pipeline. A requirement for this state is that both `in_fifo` and `out_fifo` are empty but initialized.

### RX state
Once a singular byte is placed onto the `in_fifo` the FPGA considers the first byte to be a command byte. In order to keep a consise separation between RX, processing and TX, all data associated with a command is communicated prior to command execution. During RX, each byte presented by the MCU on octo_spi is captured into in_fifo on an MCU-generated clock event. The MCU keeps ck_ss asserted while transmitting the complete command and releases it when the command has been fully transmitted. It is assumed that all data passed in this window is payload for the issued command, any data remaining on the in_fifo after processing and TX will be dropped to reset the FPGA for the next command. 

When RX ends, the first byte in in_fifo is interpreted as the command byte and passed to the decode stage.

### DECODE state

The FPGA dispatches different subroutines based on the value of the first byte transfered during RX.
For instance, in order to do an ECHO command, one would send the following hexadecimal bytes`

```
OPCODE -> EE | XX XX ... XX 
``` 

where | denotes the start of the payload.

The Decode state acts as an intermediate state between `RX` and `BUSY` and gives the FPGA a single cycle to store and evaluate the validity of the issued `OPCODE`. This could technically be done in `BUSY`, but is kept to keep the pipeline steps explicit.

### BUSY state

In this state the FPGA processes the command by delegating the work to an appropriate submodule. The `BUSY` stage is completed once `proc_done` is asserted `HIGH`. Since each submodule typically will have its own independent driver, each subprocess obliges to keep its own execute/read/write/done signaling. To keep the ownership of these signals in `SPI_processor`, there are global MUX'ed signals for signals that leave this module. For instance: `proc_done`, `proc_r_en` and `proc_w_en`.

### TX_IDLE state

Since the MCU relies on dedicated hardware, we are forced to wait a few cycles once the MCU issues a read. The delay is caused by the dedicated hardware requiring a sanity byte to be sent, and additional time for synchronizing the FPGA to take ownership of the data bus.

This state simply wait for the sanity byte and starts a 3-step synchronized handshake for taking control over the SPI bus. The TX handshake introduces a fixed delay of approximately 5 clk cycles before `tx_armed` is observed by the MCU. The handshake completion is denoted by setting `tx_armed` to `HIGH`.

### TX_SEND state

This is arguably the most involved state of the entire protocol. 

In order to securely and reliably send data from the FPGA, the TX protocol is, as the RX protocol, event driven. In other words, while ck_ss is asserted, each rising edge of ck_sck generates a TX event. The event is transferred into the FPGA's clk domain through a three-stage synchronizer. Once synchronized, the event causes the next value to be removed from `out_fifo` and loaded into `tx_out`. 

While TX is armed and ck_ss is asserted, tx_out drives the shared data bus. Each synchronized TX event advances tx_out to the next response byte.

The `tx_out` register is preloaded with the first `out_fifo` value prior to the first `ck_sck` signal in order to ensure that every event actually causes a value to be driven onto the data bus.

Once `ck_ss` is released, the FPGA treats the TX transaction as complete. Any remaining data in `in_fifo` is considered stale and is discarded before the next command transaction.


### FAILED state

A general state that any part of the system can issue a transition to. It causes the FPGA to write an `EX` onto `out_fifo`, where `X` is the error code. It then sends the FSM into `TX_IDLE`. Aka a shortcut bypassing `RX` and `Busy`. Typically used for illegal `OPCODE`s or data.


### Booting protocol

During boot (NOTE NOT BOOT STATE) time, the ready pin for the FPGA is floating, and can cause the MCU to issue commands that will force the FPGA into an illegal state. To mitigate this, the MCU is assumed to be polling a 100 byte `ECHO` command acting as a healthcheck of the stability of the SPI system during this time. Once its 100 byte payload is echoed correctly, the MCU will assume that the FPGA has stabilized, and issue an `INFO` command that sends the MCU critical information about the system configuration, such as screen dimensions, buffer sizes, and a sessionID intended to make FPGA powerloss detectable.

Note that the FPGA has no recollection of the Handshake as a concept. So in principle any command can be issued at any point in time, but it is highly recommended to do this handshake in order to ensure stability before more critical commands are issued.


## Module - Function mapping

The general mapping of modules and functions are as follows:

`SPI.sv` - General top module for the SPI subsystem. Instantiates and coordinates global signaling.
`SPI_pck.sv` - Declaration package for any constants or enum values, with a global scope.
`SPI_fsm.sv` - State machine for the SPI protocol. Decides transition rules.
`SPI_rx.sv` - Handles anything related to recieving data from the MCU.
`SPI_tx.sv` - Handles anything related to sending data to the MCU.
`SPI_processor.sv` - Dispatches submodule tasks / functions based on the current command's opcode, and decides when FPGA side processing is done and read/write signals. Sets opcode.
`command_handlers` - Any file in this folder is percieved as the processor of a given command opcode, and should be dispatched through `SPI_processor` in the opcode case handler.


## Testing the subsystem

The subsystem relies on generated IP blocks, and does therefore rely on the vivado simulation suite or an external MCU physically driving the interface in order to test it.

### Simulating in Vivado:

The first step is to include the tb_spi.sv file from the test folder into your simulation files. Also ensure that all the SPI submodules are included in your source files, including the `fifo_generator_1` and `fifo_generator_2` files.
